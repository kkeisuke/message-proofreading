# 要求分析・要件定義 — メッセージ校正デスクトップアプリ

モック実装による事前検証を経て、次フェーズで作るアプリの要求と要件を定義する。
検証で得た前提は §1.1 にまとめる。具体的な設計は本書の合意後に別途行う。

---

## 1. 背景と目的

Slack などに投稿する短いビジネスメッセージを、投稿前にローカル LLM で読みやすく直したい。

- 業務メッセージを扱うため、**外部にデータを送らない**ことが大前提[^1]
- 事前検証で動作確認したモック[^2]を、日常的に使える形に仕立て直す

### 1.1 事前検証で確認済みの前提

本書の要件は、モック実装での検証で得た次の3つの事実に基づく。

1. **エンジンは Gemma 4 E4B（ローカル実行）で実用水準**
  - 比較した Chrome 内蔵の Gemini Nano は品質が要件に届かず不採用とした[^3] [^4]
2. **LLM の出力は非決定的で、同じ入力でも当たり外れがある**
  - プロンプトの工夫だけでは安定しないため、何度でも校正し直せることを前提にする
3. **メッセージを生のまま送ると、モデルは校正せずメッセージへの「返事」を返してしまう**
  - 入力を固定の依頼文で包んで送ることで、この失敗は構造的に防げた

## 2. 利用者と利用シーン

- **利用者**: 本人のみ
  - 配布・署名・多環境対応は考えない
- **環境**: Apple Silicon の Mac
  - Docker Model Runner や Ollama などの LLM ランタイムはセットアップ済みであることを前提とする
- **利用シーン**
  - 校正: メッセージを書く → アプリに貼る → シーンを選ぶ → 校正案を確認 → コピーして投稿
  - 返信: 受け取ったメッセージを貼る → 伝えたい要点と背景を書く → シーンを選ぶ → 返信案を確認 → コピーして送信

## 3. 要求（何がしたいか）

| # | 要求 | 背景 |
|---|---|---|
| R1 | 書いたメッセージを、読みやすく簡潔な文面に直してほしい | 誤字修正だけでなく、回りくどさの解消・長文の分割まで含む |
| R2 | 送る相手・場に合わせて文体を変えたい | 同じ内容でもビジネスとカジュアルで適切な文面が違う |
| R3 | 気に入らない案はすぐ校正し直したい | 出力には当たり外れがある（§1.1-2） |
| R4 | モデルは自由に差し替えたい | 新しいモデルを試す・比較するのが容易であってほしい |
| R5 | データを外部に送らない | 業務メッセージを扱うため。本アプリの存在理由 |
| R6 | 新しい技術の学習を兼ねたい | 学習効果を優先し、アプリの規模に対して構成が重くなることは許容する |
| R7 | 受け取ったメッセージに対する返信を、自分の要点から文面に起こしてほしい | 内容は自分で決めるが、文面化に時間がかかる |

## 4. 機能要件

### 4.1 校正

- **F1**: 入力された 100 文字程度の短いメッセージを校正し、**1案**を表示する
  - 入力の文字数に上限は設けない
- **F2**: 校正のシーンを **ビジネス / カジュアル** の2択から選べる。
  - どちらのシーンでも読みやすさ・簡潔さを優先する
- **F3**: 同じ入力のまま再度校正すると、別の案が得られる
- **F4**: 校正案を**ワンクリックでコピー**できる

### 4.2 品質保証（内部動作）

- **F5**: 入力は固定の依頼文で包んで送り、モデルが返事を返す失敗を防ぐ（§1.1-3）
- **F15**: 相手のメッセージと要点をそれぞれ固定の依頼文で包んで送り、どちらが素材でどちらが指示かをモデルに取り違えさせない

### 4.3 接続設定

- **F6**: 設定画面で接続先を Docker Model Runner / Ollama のプリセットから選べる
- **F7**: 接続先から導入済みモデルの一覧を取得し、使用モデルを選べる
- **F8**: 接続先に到達できない場合、状態と対処方法を表示する
- **F9**: 設定は再起動後も保持される

### 4.4 返信

- **F10**: 相手のメッセージと自分の要点を入力すると、返信文を **1案** 表示する
  - どちらの入力も文字数に上限を設けない
  - 要点には、返信に書く内容のほかに判断の背景や前提も書ける
    - 背景は文面の選び方に反映され、返信本文には現れない
- **F11**: 返信のシーンを **ビジネス / カジュアル** の2択から選べる
  - 定義は校正と共有する
- **F12**: 同じ入力のまま再度生成すると、別の案が得られる
- **F13**: 返信案をワンクリックでコピーできる
- **F14**: 相手のメッセージと要点の両方が入力されるまで生成を実行できない

返信案は校正を通さずそのまま使う。
そのため返信の出力も、校正と同じ読みやすさ・簡潔さの水準を満たす。

## 5. 非機能要件

- **N1（プライバシー）**: メッセージの送信先は利用者が指定したローカルエンドポイントのみ。
- **N2（速度）**: ウォーム時 1案あたり数秒以内[^4]
- **N3（互換性）**: LLM との通信は OpenAI 互換 API に依存し、特定ランタイムの独自エンドポイントは使わない。
  - リクエストの拡張フィールドは、無視されても動作が壊れない範囲で送ってよい[^6]
- **N4（起動）**: アプリはランタイムの起動を待たずに立ち上がり、未接続なら F8 の案内を出す

## 6. スコープ外（今回は作らない）

- 校正案の機械検証と自動再試行[^5]
- 接続先 base URL の自由入力
- 校正履歴の保存・参照
- クリップボード連携（グローバルホットキー・自動貼り付け）
- フリー入力の追加指示（「もっと短く」など）
- ランタイム・モデルのインストール自動化
- 返信案を校正画面へ受け渡す
- 返信案の複数案の並列表示
- 相手のメッセージや返信の履歴保存
- 画面遷移をまたいだ入力と生成結果の保持
  - 画面を離れると生成は中断され、入力も消える

## 7. 制約・前提

- デスクトップアプリとして作る
- LLM は**外部ランタイム接続**方式。
  - アプリはモデルを同梱せず、OpenAI 互換エンドポイントに接続するだけ
- 技術選定は学習目的（R6）を優先する。
- 既定モデルは Gemma 4 12B（4bit 量子化）。ただし F6/F7 により固定はしない[^7]
- 校正案が原文の意味を保っているかは利用者が確認する
  - アプリは出力の妥当性を機械的に判定しない（§6）

## 8. 受け入れの目安

1. Docker Model Runner 起動中にアプリを開き、メッセージを貼ってシーンを選ぶと、数秒で校正案が表示される
2. もう一度校正すると別の案が出る
3. 設定画面で Ollama に切り替えても、同じ操作がそのまま動く
4. ランタイム停止中は、エラーではなく状態と対処方法が表示される
5. 通信先がローカルエンドポイント以外に存在しない
6. 相手のメッセージと要点を入れてシーンを選ぶと、数秒で返信案が表示される
7. もう一度生成すると別の案が出る

---

[^1]: クラウド API は却下済み。無料枠のあるクラウド API は、無料枠が例外なく入力データの学習利用と引き換えであり、業務メッセージを扱う前提と両立しない。却下の理由はコストではなくデータの扱い。
[^2]: ブラウザで動く 1 ファイルの Web アプリ + Docker Model Runner（OpenAI 互換 API を localhost に提供するランタイム）という構成だった。
[^3]: Gemini Nano の主な問題: プロンプトの例文の語彙をそのまま出力に写す、過剰な敬語、文法的に破綻した出力。プロンプト調整では解消せず、モデル能力の天井と判断した。
[^4]: Gemma 4 E4B は品質・速度とも問題なかった。Gemma 4 E4B + Metal GPU での実測で、ウォーム時 1案あたり 2.4〜2.6 秒。既定モデルを 12B に上げた後もウォーム時は数秒で、この要件を満たす。

[^5]: 校正案を原文と機械的に突き合わせ（長さ比・疑問文の保存・新規文字比率）、逸脱していれば自動で再試行する仕組みを検討していた。モックの Gemini Nano では有効だったが、Gemma 4 E4B では実機確認で十分な精度が出たため実装しない。精度が問題になれば再検討する。

[^6]: 推論モデルは答えの前に思考を出し、それが生成時間の大半を占める。実測では返信1件のうち約9割が思考だった。思考を止める指定は OpenAI の仕様になく、ランタイム側の拡張になる。エンドポイントを増やすわけではなく、対応しないランタイムは無視するだけなので、互換性は損なわれない。

[^7]: E4B から 12B へ上げた。返信の品質が E4B では届かなかったため。思考を止めたうえでも E4B より良い。
